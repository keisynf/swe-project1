# Restaurant Ordering & Status Platform — Draft Product Vision Statement

*Draft v0.1 — 2026-09-20*

## Vision statement

**For** the staff of a single dine-in restaurant — servers, kitchen, and management —
**who** lose time and accuracy to paper tickets, shouted updates, and repeated trips to the kitchen to ask whether a table's food is up,
**this platform** is a server-entered ordering and order-status system
**that** lets a server place an order against a table, tracks each item's state through the kitchen independently, derives the order's overall state from its items, and pushes a notification the moment a server needs to act.
**Unlike** paper tickets and verbal hand-offs, where the only way to learn an order's status is to go look,
**this platform** makes the state of every item and every order continuously visible to the people who need it, and tells guests where their order stands without anyone having to ask.

## The problem

In a dine-in restaurant, the state of an order lives in three places that do not agree: the server's memory, the ticket rail in the kitchen, and the food itself. Nobody can see all three. The costs are routine and compounding:

- **Servers walk to find out.** Checking whether a table's food is ready means going to the kitchen, interrupting, and coming back — repeatedly, per table, all service.
- **Ready food waits.** An item finishes and sits under the lamp until a server happens to notice. Quality drops while the guest waits.
- **Guests ask and nobody knows.** "How much longer?" has no confident answer, so the server either guesses or walks.
- **Sold-out items surface too late.** An item runs out in the kitchen, but servers keep selling it until someone tells them.
- **Orders are atomic when the food is not.** A table's appetizer, entrée, and dessert move at different speeds, yet a paper ticket treats them as one unit — so partial readiness is invisible.

## Who it's for

- **The server** (primary user): places orders against tables, needs to know without walking when an item is ready to run and when the kitchen needs something from them.
- **The kitchen** (primary user): receives orders the moment they're placed, advances items as they're cooked, and marks items sold out at the source.
- **The manager / admin**: owns the menu and the staff roster; is the only role that can change what the restaurant offers.
- **The guest** (indirect beneficiary): browses the menu and can see where their order stands, but does not place it.

## How ordering works

Orders are **entered by servers, not guests.** The server takes the order at the table and enters it into the platform, and every order carries the identifier of the server who placed it. This keeps accountability for an order with a named person and preserves the table-service interaction rather than replacing it with a guest-facing kiosk.

The guest-facing surface is therefore read-only: browse the menu, and see order status. (**Open question**, see below — the original brief described guests placing orders, and this decision reverses that. The guest-facing menu's purpose needs to be settled.)

## What the platform does

1. **Server-entered orders, attributed to a person.** A server opens an order against a table, adds items with quantity, structured modifiers, and free-text notes, and submits it. The order records who placed it.
2. **Two-level status tracking.** Every *item* has its own status; every *order* has a status derived from its items. Partial readiness becomes a first-class state instead of something the kitchen has to explain verbally.
3. **Push notifications when a server must act.** The trigger for a notification is not "something changed" but "you need to do something" — an item is ready to run, the kitchen rejected an item, an item the order depends on went unavailable.
4. **Auto-refreshing views.** Kitchen and server views update on their own; nobody reloads a page to find out whether the world moved.
5. **Sold-out at the source.** Staff can mark an item unavailable and it stops being orderable immediately, everywhere. Editing the menu itself — items, prices, modifiers — is reserved for the admin role.
6. **Structured modifiers.** Items carry defined option sets (size, preparation, add-ons, removals) rather than only free text, so the kitchen reads a consistent ticket and the price is computable.
7. **Roles with identity.** Admin, server, and kitchen are distinct roles with distinct permissions, and every staff member has their own identifier — so every order and every status transition is attributable.

## Status model (draft — for review)

You asked to look at this more closely. Here is a starting proposal, offered as a decision to make rather than a decision already made.

### Item status

| Status | Meaning | Who sets it |
|---|---|---|
| `QUEUED` | Sent to the kitchen, not started | System, on order submit |
| `PREPARING` | Kitchen is actively working on it | Kitchen |
| `READY` | Finished and waiting to be run to the table | Kitchen |
| `SERVED` | Delivered to the guest | Server |
| `CANCELLED` | Pulled before it was served | Server or admin |
| `REJECTED` | Kitchen cannot make it (ingredient out, error) | Kitchen |

### Order status

Derived from its items rather than set by hand, so the two levels cannot contradict each other:

| Status | Derivation rule |
|---|---|
| `DRAFT` | Server is still building the order; not yet visible to the kitchen |
| `PLACED` | Submitted; all live items `QUEUED` |
| `IN_PREPARATION` | At least one item `PREPARING`, none `READY` |
| `PARTIALLY_READY` | At least one item `READY`, at least one not yet `READY` |
| `READY` | All live items `READY` |
| `PARTIALLY_SERVED` | At least one item `SERVED`, at least one not |
| `SERVED` | All live items `SERVED` |
| `CANCELLED` | Every item `CANCELLED` or `REJECTED` |

"Live items" excludes `CANCELLED` and `REJECTED` items, so one rejected side dish doesn't strand an otherwise complete order.

### Questions this model raises

- **Course granularity.** Should items be grouped into courses (appetizers fire now, entrées fire later), or is a flat item list enough? Coursing is the single biggest complication a real restaurant would ask for.
- **Adding to an open order.** When a table orders dessert later, is that a new order or an amendment to the existing one? This determines whether `SERVED` is terminal.
- **Closing an order.** Is `SERVED` the end of an order's life, or is there a separate `CLOSED` state tied to the check being settled? With no payment processing in scope, `CLOSED` may have no meaning yet.
- **Rejection recovery.** When the kitchen rejects an item, does the server get a substitute flow, or just a notification and a manual fix?
- **Guest-visible status.** Does the guest see the full item-level detail, or a coarser summary ("your order is being prepared")? Item-level truth may be more anxiety than information.

## Scope decisions made

- **Dine-in only.** No takeout, no delivery.
- **Single restaurant.** Not a multi-tenant platform. Worth building so multi-tenancy isn't structurally ruled out, but it is not a v1 goal.
- **No payment processing.** The platform captures and tracks orders; money is handled outside it.
- **Servers place orders.** Guests do not.
- **Staff identity is required.** Every staff member has an identifier; every order is attributed.

## Non-goals (for now)

- Not a POS or payment system.
- Not a reservation or table-management system.
- Not inventory management — "sold out" is a manual toggle, not a decrement against stock.
- Not analytics or reporting. Attribution data is captured; reporting on it is later.
- Not guest-facing ordering.

## Course-project constraints

This is being built for a course, which sets the bar for non-functional concerns. The proposal is to keep the ones that shape the design and defer the ones that only add operational overhead:

**Keep in scope**
- **Authentication and role-based authorization.** The role model is a core product decision, not a compliance checkbox — admin-only menu editing is meaningless without it.
- **Accessibility.** Staff use this all shift on shared devices; basic keyboard operability, contrast, and touch-target sizing are cheap now and expensive to retrofit.
- **Auditability of status changes.** Who moved an item and when. It falls out of the identity model almost for free and makes the system debuggable.

**Defer, and revisit if the course requires it**
- PCI concerns — moot with no payment processing.
- Multi-location, multi-language, and offline operation.
- Real push infrastructure. In-app notification on an auto-refreshing view is likely enough; SMS and native push are not.
- Production hardening: rate limiting, high availability, disaster recovery.

## Why this is the right shape

The insight the product is built on is that **an order is not one thing.** Paper tickets and most simple ordering apps treat an order as a unit that is either done or not done, which is why servers still have to walk to the kitchen — the real state is per-item and the ticket can't express it. Modeling item status as the source of truth and deriving order status from it means the system can answer the question servers actually ask ("is *this dish* up?") instead of only the question tickets can answer ("is the whole table done?"). The notification layer then has something precise to fire on.

## How we'll know it's working

- Servers stop walking to the kitchen to check status.
- Time between an item reaching `READY` and reaching `SERVED` drops and stays low — food isn't sitting.
- Orders for unavailable items approach zero.
- Guests stop asking servers where their order is.
- Status transitions are recorded by the person who actually did the work, not backfilled later.

## Open questions

1. **What is the guest-facing menu page for, now that guests don't order?** Browsing and status only, or is there a path where a guest builds a request a server confirms?
2. **How does a guest reach their status view?** Table QR code, a code the server hands over, or a display in the dining room?
3. **Coursing** — flat item list or grouped courses? (See status model above.)
4. **Is `SERVED` terminal**, and does adding to an open order create a new order or amend the existing one?
5. **Does the kitchen have one shared view** on a shared screen, or per-cook views and per-station routing?
6. **Can servers toggle sold-out**, or only the kitchen? The kitchen knows first, but the server hears it from the guest first.
7. **How much modifier structure is enough** for v1 — a flat option list per item, or option groups with required/optional and min/max selection rules?
